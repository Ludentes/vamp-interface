# Canonical UV mapping: rules, transforms, single-image bake, identity, delight

Brainstorm following the v1 spike failure (2026-05-20). Re-derives the UV-mapping problem from first principles to find the simplest pipeline that satisfies the identity-in-texture goal.

## Rules for a canonical UV mapping (general)

- **Bijective on the surface.** Every 3D surface point ↔ exactly one (u,v) inside its island.
- **Bounded distortion.** Jacobian condition number ≈ 1 (low stretch). Conformal *xor* equiareal except on developable surfaces (Theorema Egregium) — pick the trade-off.
- **Minimum seams, hidden where they hurt least.** Fewer seams = fewer bake artifacts; more seams = less distortion.
- **Bounded UV range** in `[0,1]²` with filter margin around islands.
- **Uniform texel-per-world-area** *or* a deliberate bias toward visually-important regions.
- **High atlas packing efficiency** (filled / total pixels).

## Face-specific rules

- **Resolution follows attention budget.** Face front (eyes/lips) densest, scalp/back-of-head sparsest.
- **Seams along hairline, behind ears, under jaw, scalp midline.** Never crossing the visible portrait region.
- **Left-right symmetric.** Lets you mirror-fill unseen halves; lets symmetric edits compose.
- **Topology-aligned to anatomical loops.** Eyelid loop, lip loop, nostril, ear are distinct UV regions with sensible addresses.
- **Use FLAME-UV or FFHQ-UV layouts.** Community standards; any pretrained face-texture model worth using is trained against one of them.

## How canonical UV transforms under mesh transforms

UV is defined on the **intrinsic surface**, not on the embedding. So:

| Transform | UV change |
|-----------|-----------|
| Rigid (rotation, translation) | None |
| Uniform scale | None |
| Isometric deformation (bending, no stretch) | None |
| ARKit blendshapes (skeletal-like, small) | None — vertex UV stays glued, texture follows automatically |
| Non-isometric stretch (chibi-fy) | UV coords per vertex unchanged, but **texel-per-world-area becomes non-uniform** → texture looks stretched where geometry stretched |
| Topology change (subdivision, decimation) | Must re-derive or interpolate |

**Why this matters for our problem.** Bake once on the canonical mesh in canonical pose; ARKit drives the mesh; UV stays glued; texture follows. No re-bake per frame. Texture-in-UV-space is the right abstraction *because* of this invariance.

## Single-image → UV texture (the projective bake)

Given image `I`, canonical UV `M: surface → UV`, and known camera pose `P`, per texel `(u,v)`:

1. Invert `M` → find the surface point / face it belongs to.
2. Project that point through `P` → screen pixel `(x,y)`.
3. Visibility test (Z-buffer; reject back-facing normals).
4. If visible → write `texture[u,v] = I[x,y]`.
5. If not → inpaint queue (mirror across midline; skin-color fill; diffusion inpaint).

Conditions for this to work:

- **Pose `P` known to within ~1 px.** Registration error == texture warp.
- **Image must cover the surface you care about.** A frontal portrait can't texture the back of head — accept this and inpaint.
- **Normal-weighted blending** if more than one view.
- **Lighting in `I` must match the renderer's lighting** (or be flat) — otherwise highlights bake in and fight the renderer.

## Tool survey

For *generating* canonical UV layouts on arbitrary meshes:

- **xatlas** — open, fast, deterministic. The workhorse.
- **Boundary First Flattening (BFF)** — lowest distortion of the open academic algorithms.
- **Blender Smart UV / UV Squares** — interactive.
- **UVAtlas (Microsoft)** — tight packing.

For face meshes specifically: **don't roll your own. Use FLAME-UV or FFHQ-UV.**

For single-image-to-UV bake on an aligned mesh:

- **nvdiffrast** — UV scatter via rasterizer-driven attribute interpolation.
- **PyTorch3D `TexturesUV`** — data structure + renderer.
- **xatlas** — unwrap if needed (don't if our existing UV is already good).

Face-specific image-to-UV (deterministic-ish):

- **TF_FLAME, FFHQ-UV pipeline, AvatarMe** — photoreal-only; won't accept stylized input.
- **SOAP** — multi-view-diffusion-first; accepts stylized; closest fit to chibi but its FLAME-fit stage degrades on heavy stylization (per the authors).

Diffusion-based UV texture (general object, neural):

- **TEXGen** — wrong I/O for portraits (requires pose-aligned input image).
- **UniTEX** — TEXGen successor with topology-invariant Texture Functions. Code unreleased as of survey.
- **SeqTex** — TEXGen successor via video-diffusion priors. Object-centric, no face data.

## Identity preservation: UniTEX + InfiniteYou path

UniTEX's bottleneck for our problem is its **multi-view stage** — 6 ortho views generated by a Flux DiT. If those drift in identity, the final UV texture does too. The LTM stage that lifts views into the topology-invariant Texture Function is identity-agnostic — it just lifts whatever it gets.

Proposed graft: **replace UniTEX's image conditioning with InfiniteYou's identity injection** on the multi-view Flux DiT. Identity preserved through multi-view generation; LTM bakes faithfully.

Risks to verify before committing to this path:

- **Backbone compatibility.** Does UniTEX fine-tune from FLUX.1-dev (InfiniteYou's base) or from a custom fork? If custom, hook points differ.
- **Identity vs. multi-view-consistency tension.** Multi-view DiTs train against cross-view consistency objectives; strong identity steering might fight that and yield inconsistent views → smeared atlas.
- **Code availability.** UniTEX repo says "code will be" — not blocking-ready.

If both technical risks check out and code drops, this beats SOAP (which has no identity hook at all).

## Delight: solved by controlling the source

Classical face-bake pipelines (TF_FLAME, FFHQ-UV, AvatarMe) all spend significant complexity on **delighting** photos: estimate the lighting + remove it to recover albedo, so baked-in highlights don't fight the renderer. Whole sub-models exist for this (StyleGAN-based albedo nets, SH-light estimators).

**We don't have this problem because we synthesize the portrait.** Delight enforced at generation, not at bake:

- **Prompt tokens:** *"flat lighting, even ambient illumination, no shadows, no specular highlights, soft diffuse skin, matte vinyl finish, painted toy"*. The matryoshka work already found *"matte vinyl finish, painted toy eyes"* push this direction — those tokens are in `chibi_highstr_sweep`.
- **Negative prompt:** *"harsh shadows, rim light, dramatic lighting, specular highlights, glossy"*.
- **Flux IC-Light / Relight LoRA** if prompt-only proves insufficient. Published Flux variant takes (image, target lighting) → relit image; we'd ask for "uniform flat".
- **Canny from a flat-shaded canonical mesh render** — the ControlNet structural target is itself unlit, biasing the diffusion against putting lighting on the matched geometry.

Verify on the first render that *"matte vinyl, flat lighting"* tokens don't fight *"designer collectible figure"* tokens (they should reinforce — both push toy-photography-of-unlit-figure).

## Synthesis: what falls out

The UV-mapping problem is well-posed once these pieces are in hand:

- canonical UV layout (existing on koban; FLAME-UV if we swap mesh later)
- known pose (we render the mesh, so we know `P` exactly)
- single image generated to spec (framing controlled via mesh-canny, lighting controlled via prompt)
- projective bake (one nvdiffrast call)
- inpaint for unseen UV (mirror + skin + optional UV-space SD inpaint)

**None of this requires a learned UV-texture predictor.** Identity preservation lives at the portrait stage (InfiniteYou > PuLID). Delight lives at the portrait stage (prompt + canny-from-flat-mesh). Geometry coverage is the only thing single-frontal-view doesn't solve, and inpaint handles it.

UniTEX + InfiniteYou stays interesting as a *quality upgrade*, not a critical-path dependency — useful if we want a learned UV-space prior to clean up the bake. Worth a spike when UniTEX code drops; not blocking v2.

## Concrete proposal for v2.1

Drop SOAP from the critical path. Upgrade the v2 spec with:

1. **InfiniteYou** at the portrait stage (replace PuLID).
2. **Prompt-level delight** + mesh-canny-from-flat-render (no separate delight pass).
3. **UV-space SD inpaint** after mirror-fill (cleans seams + unseen regions, no UniTEX dependency).

UniTEX + InfiniteYou graft: standing parallel watch, spike when code drops.
